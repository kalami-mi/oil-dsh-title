# 命名与回归规范

## 标题承担什么信息

统一结构为「类别 emoji + 对象｜目标」。先识别持续产物，再前置具体对象，以全角「｜」分隔核心目标；类别不随临时动作变化，对象名称不做同义替换。命名规则的完整文本在 `lib/prompt.js`，与 Codex 版 `oil-codex-title` 的规则保持同一套语义（主线稳定、语言跟随、类别按产物、外层项目名去重、不虚构对象）。

Harness 与 Codex 的差异只在“谁来触发、怎么写入”，不在“怎么起名”：

| 方面 | oil-codex-title（Codex） | oil-dsh-title（Harness） |
| --- | --- | --- |
| 触发 | Stop Hook（外部 Python 进程） | 会话事件 `turn/end`（同进程 cordis 插件） |
| 读对话 | 经 App Server 读线程 | 直接读会话事件日志（`snapshotEvents`） |
| 起名的模型 | 起 `codex exec` 子进程 | 宿主 `llm` 服务的一次独立请求 |
| 写标题 | 官方 `thread/name/set` | 标题服务 `refresh`（写 `session/title` 事件） |
| 手动标题保护 | 首次评估后建立基线，外部改名自动锁定 | 宿主事件自带来源（`fallback`/`provider`/`user`），无需基线 |
| 并发/去重 | 进程锁 + 文件账本 | 标题服务对同一会话的取代语义 + 评估基线 |
| 归档整理 | 有 | 无 |

## 触发与状态

- 首条消息由标题服务按 `first-prompt` 自动触发；之后每轮 `turn/end`（`completed`/`max-tokens`）本插件主动 `refresh`。子会话、被打断/出错/被拦截的轮次不触发。
- 每个会话保存一个评估基线：`{ policy, title, evaluatedThrough }`。“内容没变”= 基线中的标题等于当前标题、且已评估到最新一条用户消息；“纯确认免调用”= 自基线之后新增的用户消息全部是纯确认/问候，且个数不超过 `maxConfirmationSkips`。基线只在模型给出结论（keep 或 rename）后推进；报错、超时、输出不合规不推进，下一轮自然重试。
- 策略版本 `POLICY_VERSION` 写入基线。提示词或校验规则发生语义变化时递增，各会话在下次正常检查时重新判断；不批量改历史会话。

## 容易出错的决策

- 把最后一句“提交”“继续”当作新主线：提示词要求先检查它是否服务于原来的目标；动作词不是纯确认，不免调用，但模型通常 keep。
- 只有问候却让模型虚构“一般讨论”：精确匹配的问候和确认先做确定性过滤。
- 把宿主的占位标题（首条消息前几个词）当成有意命名：请求里带 `current_title_source`，`fallback` 时提示词要求给出正式标题；模型仍说 keep 就带说明追问一次。
- 覆盖用户手动改的名：任何路径下 `source.kind === 'user'` 都拒绝；只有 `/title unlock`（显式 `override`）能解除。
- 用敏感内容起名：提示词禁止，程序再拒绝邮箱、链接、盘符路径、长数字串。
- 生成期间世界变了：又来了新用户消息 → 结果作废（`stale_result`）；用户改名 → 宿主先中止请求；插件卸载 → 取消并不写入。
- 让命名请求污染对话：命名请求不追加任何会话事件，也**不追加 `session/title-llm-request`**——会话格式迁移会严格校验该事件的形状，自造的事件有拖累会话加载的风险。

## 用真实数据与真实运行时核对出的问题

下面这些在“只用自己拼的事件和假对象”的测试里全部是绿的，是后来拿真实会话日志和真实 `dsh` 启动器才暴露的：

1. **用量口径写反了**：我按 Codex 版的口径写了“缓存含在输入内”。真实适配器（`llm-pi-ai`、`llm-deepseek`）与宿主的 token 计量器都是 **`inputTokens` 为未缓存输入，缓存另计**。`prompt_tokens=900`、缓存 100 → 输入 800 + 缓存 100。已改文档、`/title status` 与测试，端到端脚本里有断言。
2. **首轮永远看不到助手的回答**：真实会话里**所有**用户消息都在 `turn/start` 之后才写入，所以首条消息触发命名时助手还没回答；而首轮结束时我判定“内容没变”直接跳过。你的真实首条消息是粘贴的终端输出，只看它命名很不准。现在基线记录“那一轮当时是否已有回答”，没有则轮次结束时带着回答再判断一次。
3. **被中止的请求没有记账**：早期请求被轮次结束时的刷新取代而中止，但请求已发出，可能已计费，日志里却什么都没有（4 次请求只有 3 条记录）。现在记为 `aborted`、`model_called: true`、用量未知，`/title status` 计入“用量未知”。端到端脚本断言“假服务收到的命名请求数 = 日志里 `model_called` 数”。
4. **测试脚手架的竞态**：假模型在延迟之后才取预设答复，后发起的请求会先拿走第一条答复。改为发起时取。

## 开发中发现并修复的问题

这些不是假设，是实现过程中被测试或探针实际暴露的：

1. **无路由时静默失败**：脚手架里没有 `request/header`，`refresh` 得到 `no_route` 却没有任何输出，看起来就是“插件没反应”。现在写日志并告警，测试覆盖“配置了路由 / 取自请求头 / 都没有”三种。
2. **被取代的中止被记成故障**：标题服务取消旧生成时，取消原因是一个 `Error`，最初按“未知错误”记了日志并告警。现在识别 `superseded/disposed/aborted` 为正常的取代，不记录、不告警。
3. **测试假阳性**：先写的“生成期间用户改名”用例即使没有保护也会通过（假模型在改名前就返回了；即使覆盖，`rename` 也是后发生的）。Windows 定时器粒度约 15ms，脚手架自己的等待就能吃掉短延迟。规则：涉及“生成期间又发生了 X”的用例，假模型延迟取 500ms 以上，并断言必须命中的信号（请求被中止 / 日志出现 `stale_result`），不能只断言最终标题。
4. **宿主行为比预想更好**：用户改名会让标题服务立即中止进行中的命名请求，所以“写入前再查一次是否被用户固定”只是第二道防线。两道防线都留着，测试分别覆盖入口守卫与写入前守卫。

## 与本机 Codex 适配版（`%USERPROFILE%\plugins\oil-codex-title`）的关系

那个版本的本机适配（同步 Hook 秒回、`commandWindows` 不以引号开头、沙箱身份写不了状态目录因而要“投递队列 + 用户身份 worker”、配置守卫补回被 Codex 应用丢掉的插件注册）全部是**外部 Hook 进程**才有的问题。本插件是进程内的 cordis 插件，运行在 Harness 主进程里，没有 Hook、没有沙箱身份、没有 `cmd /c` 引号问题，也不需要计划任务或队列；这些都不要移植。从它借用的是：命名规则（提示词）、主线稳定与语言策略、确认免调用、用量完整记账、手动标题保护、“程序测试 / 真实触发 / 账号模型 / 桌面显示是四类证据”的验收纪律。

## 变异检查

`test/` 通过并不等于测试有效。用下面的方式检查关键守卫确实有测试守着：逐个破坏一处逻辑，确认至少一个测试变红，然后恢复。当前检查的守卫：入口与写入前的手动标题保护、纯确认免调用与连续上限、生成期间新消息作废、内容未变免调用、问候开场免调用、解除固定、被取代的中止不算故障、占位标题 keep 追问、仅正常结束触发、子会话不命名、标题结构校验、敏感信息拒绝。结果见提交说明或本文件末尾的记录；新增守卫时补一条变异。

## 回归与评测

程序测试（`npm test`）对着真实的 cordis/会话/标题服务/命令运行时，模型是可编排的假实现，验证：不错误写入、不污染会话、过期与被固定的结果被丢弃、用户保护规则、免调用规则、命令行为、bundle 装配。

**真实模型的命名质量不在这里验证。** 提示词沿用 Codex 版的规则，但本插件面对的是 DeepSeek 系列模型，语言迁移、主线稳定、类别选择等行为需要另做有限样本的模型评测（合成对话，单次、有限样本，不能据此宣称所有真实任务都准确）。每次改变提示词都必须同步补充评测案例并递增 `POLICY_VERSION`，不能只手工改好一个标题。
